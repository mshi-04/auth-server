# Go のコーディング方針

このリポジトリ（Go 製の学習用認証 API）でコードを書くときの方針。
仕様は [design.md](design.md)、パッケージ構成・責務・依存の向き・テスト方法は [architecture.md](architecture.md) を正本とし、この方針と食い違う場合はそちらを優先する。

## 構成

- 軽量な Clean Architecture として扱う。依存は内側（`auth`、`password`）へ向け、内側は外側（`httpapi`、`store/sqlite`、`net/http`、SQLite）を知らない
- パッケージは層の名前（`domain`、`usecase` など）ではなく、architecture.md の責務ごとに分ける
- インターフェースは使う側のパッケージで定義し、使うメソッドだけに絞る。実装が 1 つしかない型を、理由なくインターフェースにしない
- 「インターフェースを受け取り、具体的な型を返す」を基本にする
- ユースケースごとの入出力ポート、DTO、Presenter は作らない。`httpapi` のハンドラ内での変換で済ませる

## 関数の書き方

- 不正な入力とエラーは早期リターンで先に弾き、正常系を左端にまっすぐ書く。return の後に else を書かない
- `if err != nil { return ..., err }` の繰り返しは冗長でも許容する
- 後始末は defer で書く。トランザクションは `BeginTx` の直後、開始に成功したことを確認してから `defer tx.Rollback()` を置き、最後に `Commit` する
- `context.Context` は第 1 引数で受け取り、下の層（DB 呼び出し、`Hash`、`Verify`）までそのまま渡す。構造体のフィールドに保存しない

## 値オブジェクト

- 次のどれかに当てはまる値だけを値オブジェクトにする
  - 守るべき条件がある（検証済み、正規化済み、範囲内など）
  - 同じ基本型の値を取り違えやすい
  - 同じ検証をあちこちで繰り返している
- フィールドは非公開にし、有効な値の生成経路を、検証してから作る関数（`ParseXxx`、`NewXxx`）に限定する。外から来た値は境界で 1 回だけ解析し、内側では型だけを扱う
- Go では非公開フィールドの構造体でもゼロ値を作れる。ゼロ値で呼ばれたら明示的なエラーを返すか、ゼロ値を使わない前提を守る。ゼロ値が負荷や成功に見える挙動にしない。型ごとの扱いは design.md に定める
- JSON の入出力用の構造体、DB の行を受ける構造体、素通りするだけの値は、値オブジェクトにしない。JSON・DB 用の構造体そのものを禁止する意図ではない
- `Params` は設定入力の構造体として公開フィールドを維持し、`New` で検証する。不変の値オブジェクトにはしない
- 値オブジェクトの導入で architecture.md のインターフェース（例：`UserStore` の引数の型）が変わる場合は、先に architecture.md を更新する

## エラー

- 判定が必要なエラーはパッケージ変数（`ErrXxx`）として定義し、`errors.Is` で判定する
- 下の層のエラーは `fmt.Errorf("何をしていたか: %w", err)` で包んで返す
- 各層はエラーを自分の契約に変換する。`store/sqlite` は SQLite のエラーを `auth` のエラーへ、`auth` は `password` のエラーを `auth` のエラーへ、`httpapi` は `auth` のエラーをステータスコードへ変換する。`httpapi` が SQLite のエラーを直接見ない
- エラーは、伝播を止めた層で 1 回だけログに出す。返すエラーは最上位（`httpapi`）で記録し、握りつぶして成功や通常の失敗に変換したエラーは、変換したその場で記録する。ログに出したエラーをさらに返して、別の層で重複して記録しない。具体的な場面は design.md 6.5 を参照する
- パスワード、ハッシュ、リクエストボディを、ログにもエラーメッセージにも含めない

## 依存と組み立て

- 依存はコンストラクタ（`NewXxx`）の引数で渡し、`cmd/authd` の main で組み立てる
- DB 接続やロガーなどの依存をパッケージ変数に置かない。テストの差し込み口が必要なときだけ例外とし、最小限にとどめる
- `password` の `deriveKey` は、計算中のセマフォの枠保持を決定的に検証するための、テスト用の最小限の例外とする。差し替えるテストは並列実行せず、終了時に必ず元の関数へ戻す

## 並行処理

- ゴルーチンを起動するときは、終わる条件（ctx のキャンセル、チャネルのクローズ、`WaitGroup`）を先に決める
- 共有する資源（セマフォの枠、トランザクション）は、取得と解放を対にして defer で解放する

## 名前

- パッケージ名を文脈として使う（`password.New`。`password.NewPasswordHasher` にしない）
- ゲッターに `Get` を付けない。レシーバ名は 1〜2 文字にする
- スコープが短い変数は短い名前、広い変数は説明的な名前にする
- コメントで説明したくなったら、まず名前、型、早期リターン、関数の分割で表現できないかを考える。コメントの規約は [CLAUDE.md](../CLAUDE.md) に従う

## テスト

- テーブル駆動とサブテストで書き、境界値はテーブルの行を足して増やす
- 外部への依存は、モックライブラリではなく手書きの偽物（メモリ上の `UserStore` など）で置き換える
- テストヘルパーには `t.Helper()` を付ける
- 変更した振る舞いには、その振る舞いが壊れたら失敗するテストを付ける。必ず通ってしまうテストを書かない
- 時間や並行性に依存するテストは、`testing/synctest` などで決定的にする

## 作りすぎない

- 要件にない抽象化、設定項目、拡張点を先回りして作らない
- 迷ったら、より単純な書き方を選ぶ。複雑さが必要になった時点で足す
